# HRIS Database

MySQL 8.4 기반 HRIS(Human Resource Information System) 데이터베이스의 초기 구축 스키마와 후속 마이그레이션을 관리합니다. 조직·인사·급여·평가·결재·문서 관리에 필요한 테이블, 조회 뷰, 업무 프로시저, 검증 및 감사 트리거를 정의합니다.

| 구성 요소 | 개수 |
| --- | ---: |
| 테이블 | 총 26개 |
| 조회 뷰 | 11개 |
| 업무 프로시저 | 5개 |
| 검증·감사 트리거 | 56개 |
| SQL 스크립트 | 18개 (`001`~`018`) |

초기 구축 SQL(`001`~`014`)은 UTF-8이며 SQL 주석과 `COMMENT` 절을 포함하지 않는 규칙으로 작성했습니다. 후속 마이그레이션(`015`~`018`)에는 SQL 주석이 포함될 수 있습니다.

## 1. 실행 환경 및 적용 순서

- **DBMS:** MySQL 8.4
- **스토리지 엔진:** InnoDB
- **문자 집합:** `utf8mb4`
- **정렬 규칙:** `utf8mb4_0900_ai_ci`
- **실행 도구:** MySQL CLI 또는 `DELIMITER`를 지원하는 SQL 클라이언트

1. 신규 구축 시 InnoDB와 `utf8mb4`를 사용하는 **빈 데이터베이스**를 생성하고 선택합니다.
2. **`001`~`014` 초기 스키마**를 번호순으로 적용한 뒤 **`015`~`018` 마이그레이션**을 순서대로 적용합니다. 각 파일은 적용 이력에 따라 **한 번만** 실행합니다.
3. 운영 중인 DB에는 기존에 적용되지 않은 번호의 마이그레이션만 실행합니다. 적용 전에 반드시 백업하고, 사전 조건과 기존 데이터 호환성을 확인합니다.
4. 오류가 발생하면 실행을 중단하고 원인을 해결한 뒤 적용 이력을 확인합니다. 이미 정상 적용된 스크립트는 재실행하지 않습니다.

| 파일 순서 | 내용 |
| --- | --- |
| `001`~`006` | 업무 테이블 생성 |
| `007` | 외래 키 및 테이블 간 참조 구성 |
| `008` | 조회 뷰 생성 |
| `009` | 업무 프로시저 생성 |
| `010`~`014` | 데이터 검증·감사 트리거 생성 |
| `015` | 근태·평가 단계·HR 일정·급여명세서 테이블 및 API 필드 확장 |
| `016` | 결재 상태·권한·인증 세션 및 워크플로 관련 스키마 변경 |
| `017` | JWT 기반 인증에서 쿠키 세션 구조로 전환하는 마이그레이션 |
| `018` | 평가 회차의 회사 범위 및 제약 조건 추가 |

파일명은 `{3자리 실행 순서}_{동사}_{대상}.sql` 규칙을 사용합니다. 예: `001_create_organization_tables.sql`.

> **주의:** `001`~`014`는 신규 DB의 초기 구축 스크립트이며 기존 DB를 업그레이드하는 용도가 아닙니다. `015`~`018`은 이 초기 스키마 및 선행 마이그레이션이 적용된 상태를 전제로 합니다. 이미 배포·적용한 SQL은 수정하거나 재실행하지 않고, 변경이 필요하면 다음 번호의 마이그레이션을 추가합니다. 적용 이력은 별도로 관리하며, 서로 다른 스키마가 혼합된 상태를 `IF NOT EXISTS`로 숨기지 않습니다.

`DELIMITER`는 MySQL CLI의 명령이므로 일반 애플리케이션 DB 드라이버에 SQL로 전달하지 않습니다.

## 2. 네이밍 규칙

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| SQL 파일 | 3자리 순서 + 작업 내용, 소문자 snake_case | `007_add_foreign_keys.sql` |
| 테이블 | 소문자 snake_case, 복수형 또는 집합명 | `employees`, `assignment_history` |
| 기본 키 | 단수 엔티티명 + `_id` | `employee_id`, `approval_request_id` |
| 외래 키 컬럼 | 역할 + 참조 엔티티 + `_id` | `evaluator_employee_id`, `issued_by_user_id` |
| 일반 컬럼 | 의미가 드러나는 snake_case | `company_name`, `position_level` |
| 유니크 키 | `uq_{테이블}_{컬럼}` | `uq_users_username` |
| 외래 키 제약 | `fk_{테이블}_{참조 컬럼 또는 관계}` | `fk_departments_manager_employee` |
| 조회 인덱스 | `idx_{테이블}_{컬럼}` | `idx_employees_employee_name` |
| 검증 제약 | `ck_{테이블}_{규칙}` | `ck_approval_steps_status` |
| 조회 뷰 | `vw_{조회 목적}` | `vw_employee_directory` |
| 프로시저 | `sp_{동사}_{대상}` | `sp_change_salary` |
| 트리거 | `trg_{테이블}_{시점}_{동작}` | `trg_employees_after_update` |
| 프로시저 변수 | 매개변수 `p_`, 지역변수 `v_` | `p_employee_id`, `v_company_id` |

MySQL 기본 키의 제약 이름은 `PRIMARY`입니다. 식별자 길이는 64자 이하로 유지하며, 긴 복합 인덱스 이름은 필요에 따라 `_id`를 생략합니다. 외래 키 지원에 필요한 인덱스는 MySQL이 외래 키 이름으로 자동 생성할 수 있습니다.

모호한 컬럼명 대신 `company_name`, `employee_name`, `position_level`, `evaluation_year`, `evaluation_half`를 사용합니다. 식별자도 다음과 같이 구분합니다.

| 기존처럼 모호한 이름 | 명확한 이름 |
| --- | --- |
| `request_id`, `step_id` | `approval_request_id`, `approval_step_id` |
| `period_id`, `evaluation_id` | `evaluation_period_id`, `employee_evaluation_id` |
| `assignment_id`, `audit_id` | `assignment_history_id`, `audit_log_id` |

승인 및 반려의 결정 시각은 `decided_at`에 기록합니다.

## 3. 데이터 모델 및 무결성 규칙

- **금액:** `DECIMAL(15,2)` / **식별자:** `BIGINT` / **일시:** `DATETIME(6)`
- **문자열:** InnoDB 테이블별 `utf8mb4`, `utf8mb4_0900_ai_ci` 적용. 해당 정렬 규칙은 대소문자를 구분하지 않습니다.
- **급여:** 통화와 월급·연봉 기준은 애플리케이션에서 하나로 통일합니다.
- **조직 코드:** 부서·직급·직무·직책 코드는 회사 내에서 유일합니다.
- **회사 범위:** 직원의 현재 조직 참조는 동일 회사로 제한하고, 부서장은 해당 부서 소속 직원만 허용합니다.
- **선택적 관계:** 직원의 직책과 부서장 지정은 `NULL`을 허용합니다.
- **삭제 정책:** 외래 키는 `RESTRICT`를 사용합니다. 연결된 이력·감사 기록을 보존하고, 계정·역할·조직은 상태 변경으로 비활성화합니다. 매핑 삭제가 필요하면 해당 행을 명시적으로 삭제합니다.
- **상태 코드:** 재직 인원 및 활성 계정 조회는 `ACTIVE`, 평가 반기는 `H1`/`H2`, 결재 상태는 `PENDING`/`APPROVED`/`REJECTED`를 사용합니다. 그 외 상태·고용 형태·문서 종류·발령 유형은 서비스에서 정의합니다.
- **조직 순환:** 자기 자신을 상위 부서로 지정하는 경우는 DB 트리거가 차단합니다. 여러 단계를 거치는 순환 관계는 서비스에서 검증합니다.

자기 참조 검증 일부를 트리거로 구현한 이유는 MySQL이 `CHECK` 제약에서 `AUTO_INCREMENT` 컬럼 사용을 제한하기 때문입니다. [MySQL CHECK 제약 문서](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)

## 4. 업무 프로시저

| 프로시저 | 주요 기능 |
| --- | --- |
| `sp_set_department_manager` | 동일 회사·부서 소속 직원을 부서장으로 지정하거나 해제 |
| `sp_assign_employee` | 발령 이력 저장과 현재 부서·직급·직무·직책 갱신 |
| `sp_change_salary` | 급여 이력 저장과 현재 급여 갱신 |
| `sp_approve_step` | 담당자와 이전 단계 완료 여부를 검증해 순차 승인·반려 |
| `sp_delete_employee_without_assignment_history` | 발령 이력이 없는 오등록 직원 삭제; 다른 참조는 외래 키로 차단 |

프로시저는 내부 트랜잭션, 행 잠금 및 실패 시 롤백을 사용합니다. `SQL SECURITY INVOKER`로 실행하므로 호출 계정에 필요한 테이블 권한이 있어야 하며, 외부 트랜잭션 안에서 호출하지 않습니다.

**업무 처리 유의사항**

- 발령·급여 이력 테이블에 직접 `INSERT`해도 직원의 현재 정보는 변경되지 않습니다. 해당 업무 프로시저를 사용합니다.
- 미래 적용일은 거절합니다. 과거 적용일은 현재 값을 즉시 수정하는 정정 처리이며, 과거 이력 재계산이나 예약 발령은 별도 구현이 필요합니다.
- 결재 요청과 결재선은 서비스가 하나의 트랜잭션으로 등록하고, 처리 시작 후 결재선을 수정하지 않습니다.
- 다형적 참조값인 `reference_id`의 대상 존재 여부와 사용자 권한은 서비스가 검증합니다. 최종 결재 후 실제 인사·급여 처리를 연결하는 것도 애플리케이션 책임입니다.

## 5. 감사 로그와 접근 제어

### 5.1 감사 주체 전달

서비스는 변경 작업을 실행하는 **같은 DB 연결**에 인증 사용자 ID와 요청 IP를 설정합니다.

```sql
SET @hris_actor_user_id = 1;
SET @hris_actor_ip_address = '127.0.0.1';
```

여기서 사용자 ID는 실제 `users.user_id`입니다. 연결 풀에 반환하기 전에는 성공·실패와 무관하게 두 값을 초기화합니다.

```sql
SET @hris_actor_user_id = NULL;
SET @hris_actor_ip_address = NULL;
```

초기 데이터 적재와 같이 인증된 작업 사용자가 없는 경우에는 `NULL`을 허용합니다. 프로시저에 전달하는 사용자 ID와 DB 세션의 사용자 ID는 서비스가 인증 결과에 따라 설정해야 합니다. **SQL 자체는 로그인 사용자를 인증하지 않습니다.**

감사 트리거는 `INSERT`/`UPDATE`/`DELETE` 변경 전후를 JSON으로 기록하되 비밀번호 해시는 저장하지 않습니다. 감사 로그에는 개인정보 및 급여 데이터가 포함될 수 있으므로 조회 권한과 보존 기간을 별도로 관리하고, 업무 계정에는 감사 로그의 `UPDATE`/`DELETE` 권한을 부여하지 않습니다.

### 5.2 애플리케이션 권한과 자연어 조회

- `users`, `roles`, `permissions`는 **애플리케이션 권한** 데이터입니다. MySQL 접속 계정이나 `GRANT`를 자동 생성하지 않습니다.
- `vw_user_effective_permissions`를 사용하여 서비스에서 작업 권한을 검증합니다.
- 자연어 질의용 조회 뷰는 `vw_nl_employee_directory`, `vw_nl_org_headcounts`입니다.
- 해당 뷰는 회사별 행 접근 제어를 자동 적용하지 않습니다. 서비스가 허용 회사·허용 뷰·`SELECT` 구문을 검증해야 합니다.
- 자연어 조회에 사용할 별도 읽기 전용 DB 계정에는 허용 뷰의 `SELECT` 권한만 부여하고, 뷰의 `DEFINER`는 배포 환경의 계정 정책에 따라 관리합니다.
- LLM 호출, SQL 검증, 질의 실행 및 결과 표현은 애플리케이션 구현 범위입니다.
